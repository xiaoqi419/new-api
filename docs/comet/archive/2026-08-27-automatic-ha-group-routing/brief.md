# Outcome

保留 new-api 原版 API Key 候选分组和兼容自动分组能力，撤销本 change 新增的跨分组、跨倍率“自动 / 高可用”虚拟组。新增由管理员配置的固定分组渠道调度池：每个池绑定一个精确实际分组、一个精确 `Channel.Type` 和明确勾选的渠道集合。命中调度池的同步文本请求只在池内按现有 Priority、Weight 和 fallback 规则选路；渠道 A 在首字节前出现允许切换的可用性错误时，在现有 `RetryTimes` 预算内排除 A 并切换到池内同组、同原始模型、同类型的 B，未勾选渠道 C 不参与首次选路或故障切换。A 恢复后重新进入池内调度。

同时在渠道监控中新增按渠道和模型展示的缓存率预测。系统在消费日志写入时保存归一化输入 Token、缓存读取 Token 和缓存写入 Token，使用最近 7 天小时桶、24 小时半衰期的 Token 加权结果预测未来 24 小时缓存命中率；数据不足时显示原因，不伪造 `0%`。

- 原样保留 API Key 的 `GroupSwitchEnabled`、候选分组、失败阈值和冷却时间，以及现有 `AutoGroups/AutoGroupRoutes/CrossGroupRetry` 兼容链；本次不新增、重写或扩展自动分组。

- 在 Routing Reliability 管理界面新增渠道调度池配置。每个启用池具有稳定 ID、名称、精确实际分组、精确 `Channel.Type` 和至少两个不重复的渠道 ID；同一 `(group, channel_type)` 最多一个启用池。
- 保存时校验渠道存在、类型相同且通过 `Channel.GetGroups()` 精确属于目标分组；运行时防御性忽略已删除、已禁用、类型或分组已不匹配、模型或路径不支持的池成员。
- 一个实际分组只要存在启用池就进入受管模式。首次候选是该分组全部启用池渠道白名单的并集；首次选中渠道后锁定其所属池和 `Channel.Type`，所有重试只在该池内进行。未勾选 C 不得被普通选路或数据库回退选中；全部启用池都无可用成员时 fail closed。没有启用池的分组保持原版选路。
- 首次请求在合格池成员中继续使用现有 `priority + weight + fallback` 规则选择 A。池中只剩一个合格成员时仍可使用，但没有可切换的 B。
- 仅在同步文本 relay、响应首字节发出前且 `RetryTimes` 尚有预算时，记录请求内失败渠道集合并选择替代渠道。替代渠道必须仍在同一池内，并支持相同原始请求模型和路径。
- 重试重新从剩余候选的最高优先级档选择，避免 retry 序号跳过可用主备渠道；同优先级仍沿用 Weight，但当前请求不得再次选择已失败渠道。
- 可切换错误复用现有 `AutomaticRetryStatusCodes`，并复用不依赖自动禁用总开关的 `AutomaticDisableStatusCodes` 与 `AutomaticDisableKeywords` 匹配；网络连接错误和超时继续按现有安全重试规则处理。
- 内存缓存和数据库回退路径执行相同的池白名单、失败 ID、精确分组、原始模型、请求路径和类型过滤。
- A 未被自动禁用时，请求结束即清除排除集合，下一请求重新按优先级尝试 A；A 被自动禁用时，复用 scheduled/passive channel test 和 `AutomaticEnableChannelEnabled` 恢复，并在恢复后立即重新插入渠道缓存。
- 在消费日志新增 `input_tokens`、`cache_read_tokens`、`cache_write_tokens` 三个 Int64 数值列；OpenAI/Gemini 使用归一化总输入，Anthropic 总输入包含普通输入、cache read 和 cache write，可靠 `billingUsage.InputTokens` 优先。
- 缓存率定义为 `SUM(cache_read_tokens) / SUM(input_tokens) * 100%`；cache write 不进入分子。异常、非正输入或不满足 Token 不变量的行不参与预测并记录告警。
- 渠道监控继续一次性按渠道、模型、小时聚合。观察值按所选监控窗口 Token 加权；预测固定使用最近 7 天，按 `2^(-age_hours/24)` 衰减，表达未来 24 小时预期缓存率。
- 预测至少需要 20 个有效成功请求、10,000 输入 Token、3 个活跃小时和正缓存能力证据；不足时返回结构化原因。预测为有效 `0%` 时必须显示 `0.0%`。
- 渠道级预测按 Token 合并具备缓存证据的模型，不对模型百分比做算术平均；模型级和渠道级均返回观察值、预测值、样本量、支持度和窗口。
- 渠道监控列表与详情复用同一响应式展示：渠道标题下方显示紧凑摘要，模型指标行显示预测缓存率，Tooltip 解释观察值、样本、窗口、支持度和预测不是上游保证。
- SQLite/MySQL/PostgreSQL 使用 GORM 增量迁移；ClickHouse 建表和 `ADD COLUMN IF NOT EXISTS` 同步补齐 `first_token_ms` 及三个缓存遥测列。旧日志不回填，零值旧行不参与预测。
- 保留已完成的“渠道测试模式”下拉框中英文长文案、窄屏和视口宽度修复。
- 更新聚焦 Go/前端测试、全部现有语言 i18n 和 changelog，使界面只描述当前固定组调度池、渠道切换和缓存率预测。

# Non-goals

- 不由新渠道调度池切换 API Key 实际分组；即使另一分组倍率同为 `0.2`，也不得成为替代渠道。
- 不跨 `Channel.Type`；OpenAI 只能切换 OpenAI 类型渠道，Anthropic、Gemini 和其他类型同理。
- 不新增渠道级倍率字段，不比较 `float64 == 0.2`；同倍率由固定 `using group + origin model` 保证。
- 不删除、不重构原版显式候选分组切换和 retired 兼容链，也不改变用户主动配置该原版功能时的既有行为。
- 不为每个池复制独立重试次数、状态码、关键词、测试周期或恢复策略；全部复用现有全局可靠性设置。
- 不对指定渠道、渠道亲和要求停止重试、客户端取消、`SkipRetry`、已写出首字节/首 Token、图片、音频、视频、批处理或异步任务执行自动渠道切换。
- 不并行双发，不在没有池内替代渠道时回退到未勾选渠道、其他类型或其他分组。
- 不承诺同优先级 A/B 恢复后固定选择 A；确定主备顺序继续使用 Priority 或 fallback。
- 不在监控 API 请求时逐行读取或解析历史 `Log.Other` JSON，不回填语义不稳定的旧缓存数据，不引入机器学习模型或缓存率趋势图。
- 本地验收前不提交、推送、合并、部署，不修改生产数据库和线上配置。

# Acceptance examples

- A1：撤销本 change 新增的虚拟自动组、跨组自动 HA、跨组计费/恢复逻辑后，原版 API Key 候选分组字段、界面和 Relay 行为保持可用，旧兼容链未被删除。
- A2：管理员可创建、编辑、启停和删除多个调度池；每个池绑定精确分组、精确 `Channel.Type` 和显式渠道 ID 集合，同一 `(group, type)` 不允许两个启用池，保存无效或不足两个成员的池会得到可操作错误。
- A3：实际分组存在启用池时，首次候选只来自该分组全部启用池的白名单并集；选中 OpenAI A 后重试锁定 A 所属池和 OpenAI 类型。OpenAI 池仅勾选 A/B 时，同组同类型未勾选 C 不参与；全部启用池无人可用时 fail closed。没有启用池的分组保持原版选路。
- A4：渠道删除、禁用、改类型、移出分组或失去模型/路径能力后，运行时忽略失效池成员且管理界面保留可识别的失效项供清理；配置热更新无需重启。
- A5：固定分组文本请求首次选择高优先级 OpenAI A；A 出现允许切换的错误且 `RetryTimes=1` 时，下一尝试选择池内同组同模型 OpenAI B，不再次选择 A。
- A6：A -> B 前后实际分组和原始模型不变，`UsingGroup`、`GroupRatioInfo`、模型价格、预扣和结算不因渠道切换变化；系统不比较或存储渠道级浮点倍率。
- A7：`RetryTimes=0` 不切换；预算耗尽后不继续尝试。没有合格 B 时返回最后一个真实上游错误，不使用“无渠道”覆盖，也不跨边界兜底。
- A8：配置的重试状态码、自动禁用状态码、关键词、网络连接错误和超时可以在首字节前触发切换；未配置客户端 `400`、取消、内容审核、`SkipRetry`、指定渠道和亲和停止条件不触发。
- A9：内存缓存和数据库回退路径都严格执行池白名单、失败 ID、精确分组、原始模型、请求路径和首次渠道 `Channel.Type`；同优先级也不会在同一请求再次命中 A。
- A10：新请求不继承失败 ID。A 未禁用时重新按优先级参与；A auto-disabled 后由现有渠道测试成功恢复并立即重新进入缓存。A Priority 高于 B 时下一请求回到 A，同优先级保持 Weight 分流；手工 disabled 不自动恢复。
- A11：Routing Reliability 的调度池列表和编辑器在中英文、亮暗主题、320px 与 1440px 下可完整配置分组、类型和渠道，长名称不溢出；渠道测试模式下拉框修复保持有效。

# Constraints and invariants

- 以当前工作树 HEAD `c59fd1bec` 为功能基线，不能用更旧的 `origin/main` 整体覆盖；只撤销当前 change 引入的跨组自动 HA 增量。
- 遵循 Router -> Controller -> Service -> Model 分层，复用现有 Relay、渠道缓存、ConfigManager、渠道测试、自动恢复和监控聚合链路。
- “同倍率”的稳定业务约束是固定 `using group + origin model`；禁止用浮点相等或 epsilon 推断渠道身份。
- “同供应商”的本期定义是 `Channel.Type` 精确相等；Advanced Custom 同属一个 Type，本期不再拆分其内部 converter 身份。
- 调度池渠道 ID 是正向白名单；池命中后任何选路路径都不得扩大集合。请求内失败集合有界于池成员数且不跨请求。
- 固定组渠道故障转移不得推进原版 GroupSwitch 候选索引或失败计数；原版能力只在用户原有配置流程中运行。
- 缓存预测只使用成功消费日志的归一化数值列；观察/预测均为 Token 加权，未知不等于零。
- 新日志 Token 列使用 Int64；不作为查询过滤条件，不新增高成本组合索引。ClickHouse 显式维护兼容 DDL。
- 不改变 relaykit 模块独立性；若触及 relaykit 公共 API，额外执行 `GOWORK=off go build ./...`。
- 保留用户和其他代理已有改动；实现只发生在 `E:\code\new-api\.worktrees\automatic-ha-group-routing`。

# Decisions

- 保留原版候选分组；取消的是本 change 新增的统一虚拟自动组和跨倍率 HA 编排。
- 管理员通过多个显式调度池决定 A/B/C 哪些渠道参与；同一精确分组和类型最多一个启用池，池配置以单个 JSON Option 原子保存并热应用。
- 分组存在启用池时，首次选路限定在全部池白名单的并集；首次选中后重试锁定具体池并 fail closed，不让未勾选 C 或其他类型池悄悄接管。C 仍可保持启用并服务未受这些池管理的其他分组或指定渠道操作。
- 首次渠道类型和池 ID 成为请求级边界；可重试错误发生后立即排除失败渠道，在下一次重试从池内剩余最高优先级档重新选择。
- 可重试错误和自动禁用状态码/关键词共享纯匹配语义，但渠道切换不依赖全局自动禁用开关。
- 长期恢复依赖原版自动禁用、scheduled/passive channel test、自动恢复和 Priority，不保留候选组专用恢复任务或高价组 sticky。
- 缓存遥测使用三个专用数值列，不在请求时解析历史 JSON；旧日志不回填，部署后先显示收集中。
- 预测是可解释的指数衰减 Token 加权估算，不是机器学习模型或上游承诺；固定最近 7 天预测未来 24 小时。
