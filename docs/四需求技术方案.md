## 需求 1：用量记录页新增「用户 Token 排行」+ 下钻到该用户用量明细

### 现状
- 已有独立页 `web/classic/src/pages/UserRanking/index.jsx`，接口 `GET /api/user_ranking/?dimension=tokens|quota|requests|ip_count|ip_per_minute`，后端 `controller/user_ranking.go` + `model.GetUserConsumeRanking`。
- 用量记录页 `web/classic/src/components/table/usage-logs/`，筛选器 `UsageLogsFilters.jsx` 已含 `username` 字段（管理员可见），明细表已支持按 user/username 过滤。

### 方案（复用现有排行接口，主要前端改动）
1. 在用量记录页（仅管理员）顶部加一个可折叠的「用户 Token 排行」面板：
   - 复用 `GET /api/user_ranking/?dimension=tokens&start&end&limit=20`（时间范围跟随日志页的 dateRange）。
   - 展示：排名 / 用户ID / 用户名 / Token 数。
2. 下钻：点击排行行 → 把该行 `username`（或 user_id）写入日志筛选表单并触发 `refresh()`，明细表即显示该用户的用量记录。
   - 通过 `formApi.setValue('username', row.username)` + `refresh()` 实现，无需新接口。
3. 面板默认折叠，避免影响现有明细浏览；非管理员不显示。

### 涉及文件
- 前端：`usage-logs/index.jsx`（挂载面板 + 下钻回调）、新增 `usage-logs/components/UserTokenRankingPanel.jsx`、`UsageLogsFilters.jsx`（暴露 setValue 能力，已有 formApi）。
- 后端：**无需改动**（复用 user_ranking）。若要限定"当前筛选条件下的 Token 排行"，才需要扩展后端；一期先用全局 tokens 排行。

### 工作量：小（纯前端，半天级）
### 风险：低。排行接口已存在且带时间范围安全默认。

## 需求 2：API Key（令牌）并发实时统计

### 现状
- Token 模型有 `MaxConcurrency`（令牌级最大并发上限，0=不限），`model/token.go`。
- 并发限流器 `service/concurrency_limiter.go`：
  - **Redis 模式**：用 ZSET `concurrency:token:<id>` 计数，`ZCARD` 即当前在途并发数（带 TTL 自愈）。
  - **内存模式**：`golang.org/x/sync/semaphore`，**读不出当前占用量**（信号量不暴露计数）。
- 中间件 `middleware/concurrency-limit.go` 调 `AcquireConcurrency("token", tokenId, max)`。

### 方案
1. 后端加只读函数 `service.GetConcurrencyInUse(scope string, id int) (int, bool)`：
   - Redis 模式：先 `ZRemRangeByScore` 清理过期条目，再 `ZCARD concurrency:token:<id>` 返回实时值，ok=true。
   - 内存模式：semaphore 无法读取 → 返回 ok=false（前端显示"—"或仅显示上限）。
2. 新接口 `GET /api/token/concurrency`（管理员或本人令牌）：批量返回 `{token_id: {in_use, max, supported}}`。
   - 为避免 N 次 Redis 往返，用一次 pipeline 批量 ZCARD。
3. 前端令牌列表（`components/table/tokens/`）加一列「并发」：显示 `in_use / max`（如 `3 / 10`）；不支持实时时显示 `— / max` 或仅 `max`。
   - 可加轮询（如每 5s 刷新该列），或手动刷新按钮。

### 涉及文件
- 后端：`service/concurrency_limiter.go`（加只读读数函数）、`controller/token.go`（新 handler）、`router/api-router.go`（注册路由）。
- 前端：tokens 列定义 + 拉取并发数据的 hook。

### 关键约束
- **仅 Redis 部署能看到实时并发**；内存模式只能显示上限。需在 UI 注明。
- 读数要清理过期 ZSET 条目，否则崩溃残留会虚高。

### 工作量：中（后端读数 + 接口 + 前端列 + 轮询，1 天级）
### 风险：中（依赖 Redis；内存模式功能降级）。

## 需求 3：渠道「兜底渠道」配置（备用 apikey + url + 从 url 获取模型）

### 现状
- 渠道模型 `model/channel.go` 已有 `Key`、`BaseURL`、`Models`、以及 `Setting *string`（JSON text，存渠道额外设置，天然可扩展，无需加列）。
- 已有拉取上游模型接口：`POST /api/channel/fetch_models`（body 传 base_url + key，返回模型列表）、`GET /api/channel/fetch_models/:id`。前端 `ModelSelectModal.jsx` 已在用。
- 已有渠道失败重试机制（`middleware/distributor.go` 的 `original_model` + 重试到下一渠道）。

### 方案
把「兜底渠道」作为**渠道级配置**存入 `Setting` JSON（键如 `fallback`）：
```jsonc
"fallback": {
  "enabled": true,
  "base_url": "https://backup.example.com",
  "key": "sk-backup-xxx",
  "models": "gpt-4o,claude-3-5"   // 可由"获取模型"按钮回填
}
```

1. **前端渠道编辑表单**（`EditChannelModal.jsx`）新增「兜底渠道」区块：
   - 输入：启用开关、备用 Base URL、备用 API Key、模型列表 + 「获取模型」按钮（复用 `fetch_models`，用兜底的 base_url+key 拉取并回填 models）。
   - 保存时写入 `channel.setting.fallback`。
2. **后端 relay 兜底转发**：当该渠道请求失败（连接失败/5xx/超时等可重试错误）且配置了 `fallback.enabled`：
   - 用兜底 base_url + key 重发同一请求（同 model 或经 fallback.models 校验），成功则返回。
   - 需要在 relay 失败处理链（`relay/` + `middleware/distributor.go` 重试逻辑）里插入"渠道自带兜底"这一层，位于换渠道重试之前或之后（需定策略）。
3. 「获取模型」按钮：直接复用 `POST /api/channel/fetch_models`，传兜底的 base_url+key。

### 涉及文件
- 后端：`model/channel.go`（Setting 解析辅助，如 `GetFallbackConfig()`）、relay 失败处理（`relay/relay-text.go` / `relay/helper` / `middleware/distributor.go` 相关重试点）、可能新增兜底转发 helper。
- 前端：`EditChannelModal.jsx`（表单区块 + 获取模型按钮接线）。

### 关键决策点（需实现时定）
- 兜底触发条件：哪些错误码/错误类型触发（建议：网络错误、5xx、超时；不含 4xx 鉴权/参数错误）。
- 兜底与"多渠道重试"的顺序：先本渠道兜底再换渠道，还是反之。
- 计费：兜底成功仍按原渠道/原模型计费（避免影响账单口径）。
- 安全：兜底 key 属敏感信息，存储/回显需与现有 key 脱敏一致（`SaveWithoutKey` 等模式）。

### 工作量：中大（relay 链路改动需谨慎，1.5-2 天）
### 风险：中高（触碰计费/重试关键路径，需严格测试不破坏现有转发与账单）。

## 需求 4：发票申请 / 开票（用户申请 + 管理员开票上传 PDF + 双方查看记录）

### 现状
- **后端零基础**：无 invoice 相关表/接口/模型（仅 default 前端 i18n 有零星词）。
- 有成熟的用户端/管理端路由分组（`selfRoute` 用户自身，`adminRoute`/`AdminAuth()` 管理员）与文件返回模式可参考。

### 方案（全新功能，本地磁盘存 PDF）

#### 数据模型（新表 `invoice_requests`，兼容三种 DB）
```go
type InvoiceRequest struct {
    Id            int    // GORM 主键
    UserId        int    `gorm:"index"`
    Username      string
    Amount        int64  // 申请开票金额（quota 或货币，按现有口径）
    Title         string // 发票抬头
    TaxNumber     string // 税号
    Type          int    // 抬头类型：个人/企业
    Email         string // 接收邮箱
    Remark        string
    Status        int    // 0待处理 1已开票 2驳回
    InvoiceFile   string // 已开票 PDF 相对路径
    RejectReason  string
    CreatedTime   int64
    ProcessedTime int64
    ProcessedBy   int    // 处理管理员 id
}
```
- 迁移用 `AutoMigrate`，遵循 AGENTS 的跨库规范（不用 SERIAL/AUTO_INCREMENT，不用 DB 特有类型）。

#### 用户端（钱包页新增「发票」区）
- `POST /api/invoice`（本人）：提交申请（金额/抬头/税号/邮箱/备注）。
- `GET /api/invoice/self`：查看本人申请记录 + 状态 + 下载已开票 PDF。
- `GET /api/invoice/download/:id`：下载本人发票 PDF（校验归属）。

#### 管理员端（控制台新增「发票管理」）
- `GET /api/invoice/admin`：分页列出所有申请（可按状态筛选）。
- `POST /api/invoice/admin/:id/issue`：上传 PDF（multipart）+ 标记已开票，存本地磁盘。
- `POST /api/invoice/admin/:id/reject`：驳回 + 原因。
- 上传的 PDF 存到本地目录（如 `./data/invoices/{id}.pdf` 或 `common.UploadPath`），DB 存相对路径。

#### 前端
- 用户：`components/topup/` 或钱包页加「申请发票」弹窗 + 「我的发票」列表（状态、下载）。
- 管理员：新增 `pages/Invoice/` 或 `console/invoice` 页面 —— 申请列表 + 开票（上传 PDF）/ 驳回操作。
- 侧边栏（`hooks/common/useSidebar.js`）加管理员「发票管理」入口。

### 涉及文件
- 后端：新增 `model/invoice.go`、`controller/invoice.go`、`router/api-router.go`（用户/管理员路由）、`model/main.go`（AutoMigrate 注册）、文件存储用现有上传路径逻辑。
- 前端：用户端弹窗+列表、管理员页面、侧边栏入口、i18n。

### 关键决策点
- 金额口径：按 quota 还是货币金额？是否校验用户实际充值/消费额度上限。
- PDF 存储目录 + 大小/类型校验（仅 pdf，限大小），下载鉴权（仅本人或管理员）。
- 是否邮件通知用户"发票已开具"。

### 工作量：大（建表 + 6~7 个接口 + 用户端 + 管理端 + 文件上传/下载 + i18n，2-3 天）
### 风险：中（新功能不碰核心链路，但文件上传/下载需注意鉴权与路径穿越安全）。

## 建议实施顺序
1. **需求 1**（最小，纯前端，先出效果）
2. **需求 2**（后端读数 + 前端列，中等）
3. **需求 4**（发票，独立大模块，不碰核心链路，可稳步做）
4. **需求 3**（兜底转发，触碰计费/重试关键路径，风险最高，最后做并重点测试）

## 全局注意
- DB 迁移三库兼容；JSON 走 common 包；计费不变口径。
- 敏感信息（兜底 key、发票税号）脱敏 + 鉴权。
- 文件上传做类型/大小校验，下载防路径穿越。
- 每个需求实现后用 agent-browser 在 dev(:5174) 验证 light+dark。
